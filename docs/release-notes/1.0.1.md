# ExitLane 1.0.1

This patch release adds independent WireGuard identities for multiple consumers and
makes the appliance easier to read and operate. A router, NAS and container gateway
can each have a named peer with its own key, tunnel address, connection activity and
individual actions. They still share one selected VPN exit and protection policy;
this release does not add per-device provider selection. The compact dashboard shows
the current VPN exit, ingress devices, protection and health together. Peer actions
move into each device's menu, and management-routing lock failures appear in Activity.

Native Debian 13 amd64 supports NordVPN, Mullvad, PIA and imported Proton WireGuard.
The Docker appliance supports Mullvad, PIA and imported Proton on Linux amd64 with
rootful Docker Engine 28 or newer, Compose v2, TUN, `NET_ADMIN`, read-only root and
durable state. NordVPN remains native-only. Live commercial PIA/Proton
interoperability remains unqualified; synthetic tests do not establish it.

## Security and reliability

The [2026-10-06 internal defensive assessment](../security/daybreak-blue-assessment-2026-10-06.md)
found one Medium initial WireGuard adoption consistency issue and one Low native
evidence output-confinement issue. Separate PRs [#143](https://github.com/kevindraai/exitlane/pull/143)
and [#144](https://github.com/kevindraai/exitlane/pull/144) fixed and deterministically
retested them. The original finding severities remain in the assessment report.
The native collector gathers source-bound, read-only package/advisory evidence;
collection by itself does not decide vulnerability applicability or qualify a release.
PR [#146](https://github.com/kevindraai/exitlane/pull/146) fixes gaps found during real
appliance qualification: full Debian advisory input, a verified public advisory
example, installed Python vendor metadata and signed APT coverage. Scanner findings
and any remaining coverage limits stay visible.

## Upgrade from v1.0.0

Create and verify an encrypted backup before upgrading. Preserve an off-appliance
copy, the previous exact source or image identity, and local network/proxy settings.
Native operators should follow [upgrade and recovery](../upgrade-and-recovery.md):
use a separate checkout of the published `v1.0.1` tag and run the installer, which
takes a protected pre-upgrade snapshot and rolls back on failure. Confirm service
health and authenticated access, then check that the existing router profile still
works and appears as the first named device. Its server/client keys and network
settings should be preserved. Add other consumers as separate peers, and verify
their handshakes, DNS and expected public exit from the actual clients.

Docker operators should follow [image upgrade and rollback](../docker-deployment.md#upgrade-and-rollback).
Use the published v1.0.1 image digest and version-matched deployment files, retain
the previous digest and compatible volume backup, and verify provider-or-block
behavior after recreation. Neither HTTP health nor a screenshot proves protected
client egress. The v1.0.0 tag and image remain immutable rollback references; do not
reuse the `v1.0.0` deployment files with an unverified newer image.

## Release evidence

The [published v1.0.1 release](https://github.com/kevindraai/exitlane/releases/tag/v1.0.1)
must provide the final source/tag SHA, artifact checksums, native installation and
v1.0.0 upgrade/recovery results, required checks and scan dispositions, and the
Docker image digest, SBOM, provenance and exact-image qualification receipts.
Public Proxmox and anonymous registry-pull acceptance are recorded there when
completed. This source document records the intended path and does not assert
that those release-specific checks have already passed.
