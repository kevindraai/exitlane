# ExitLane 0.3.0-rc.4

This release candidate consolidates the post-rc.3 appliance work. Runtime version is
`0.3.0-rc.4`, tag `v0.3.0-rc.4`, and Python package version `0.3.0rc4`.
It remains pre-release software for a trusted management network.

## Highlights

- Install a Proxmox appliance through the guided public launcher, with one published tag
  governing the helper and application.
- Recommended/Advanced setup, console credentials, SSH keys, secure SSH defaults, clearer
  output and private logs make installation and failures easier to operate.
- Native NordVPN, Mullvad, PIA and imported Proton profiles share the existing provider UI.
- Docker D1–D7 source is delivered with synthetic whole-host packet/restart qualification.
  **Docker remains experimental/unsupported. No official Docker image is published.**

## Since rc.3

### Proxmox installation

The Community-Scripts-style public launcher replaces manual cloning of the helper as the normal
operator path. It resolves the published release policy and verifies the downloaded tagged helper
against the GitHub blob/size metadata; the helper installs the application from that same tag.
This is transport/integrity checking through GitHub, not an independent authenticity root.

Recommended and Advanced modes support console/root credential choices and SSH public keys.
SSH is key-only by default; password SSH requires an explicit operator choice. Standard output
keeps progress readable; verbose mode and root-only host installation logs retain diagnostics.
Secrets are masked and excluded from diagnostic output. Failed installations preserve partial CTs.
PVE DNS/default-route readiness includes `_apt` resolver access, two stable readiness rounds,
strict repository failures and bounded retries. See [Proxmox installation](../proxmox-lxc.md).
Fresh PVE qualification also repairs unintended DHCPv6 startup, enables the nesting prerequisite
for existing systemd isolation, and preserves socket-activated SSH access when applying policy.

### PIA and Proton

These implementations were already included in rc.3; rc.4 consolidates their documentation and
regression evidence. PIA is first-class ExitLane-managed WireGuard, with authentication, region
discovery, region/provider switching and fail-closed routing. It requires no PIA app or OpenVPN.

Proton uses imported WireGuard profiles with bounded safe parsing, encrypted private-key storage,
profile selection/switching and the generic provider lifecycle. No Proton CLI, NetworkManager or
desktop keyring is required. Direct providers currently offer IPv4 egress; IPv6 remains protected
and blocked, rather than supported egress. See [PIA](../pia.md) and [Proton](../proton.md).

### Security

All post-Daybreak WireGuard input/configuration hardening, restore validation, streamed request
limits, provider bounds and archive limits remain included. The Daybreak assessment is internal
Blue-assisted defensive evidence, not an independent external penetration test. See the
[assessment](../security/daybreak-blue-assessment-2026-09-30.md) and
[current assurance matrix](../security/security-assurance-matrix.md).

### Docker experimental work

The same core now has explicit native/container capability boundaries, supervised container-native
WireGuard, provider-or-block routing, and durable state/backup/recovery. Mullvad, PIA and imported
Proton profiles are the direct container providers. Candidate image/Compose implementation,
whole-host synthetic D6 packet/restart qualification and D7 release integration are delivered.

Stock official NordVPN Linux client 5.4.0 was independently assessed as **NOT SUITABLE** for this
qualified container contract, including mandatory repeated IPv6 kernel/sysctl mutation under the
constrained read-only runtime. No forbidden privilege expansion was adopted. This is a runtime
compatibility decision; native NordVPN remains supported. See the [research](../nordvpn-container-research.md).

**Docker remains experimental/unsupported. No official Docker image is published.** rc.4 does
not publish an image or authorize GHCR workflow dispatch. See the [candidate](../docker-appliance-candidate.md)
and [release qualification](../qualification/0.3.0-rc.4.md).

### Maintenance

Native installation compares application bytes when copying a release, preventing equal-size,
equal-timestamp files from retaining content from the previous release.

Development urllib3 and Ruff were refreshed, immutable CodeQL action pins updated, and current
documentation reconciled. Candidate image builds consume supported Debian 13 security updates.
The required Python formatting gate is applied without syntax-tree changes. Artifact qualification
also repairs missing packaged GPL/third-party notices and local Help guides, including standalone
wheel guide lookup. Synthetic native packet tooling now explicitly enables forwarding only inside
its disposable namespace rather than inheriting the development host setting.

## Installation

Supported/reference platform: **Debian 13 amd64**, including a **privileged Proxmox LXC** with
TUN, WireGuard, routing and nftables authority. Other architectures, Debian releases and
unprivileged LXC are not supported release targets. Keep management on a trusted network.

On the Proxmox host, as root:

```bash
bash -c "$(curl -fsSL https://raw.githubusercontent.com/kevindraai/exitlane/main/installer/proxmox.sh)"
```

The moving bootstrap resolves a published release, then fetches and executes its exact tagged
helper/application. It does not install `main`. See the guide for inspect-first and Advanced use.

For an already prepared supported native host/LXC, after publication:

```bash
git clone --branch v0.3.0-rc.4 --depth 1 https://github.com/kevindraai/exitlane.git
cd exitlane
sudo ./installer/install-debian.sh
```

Open `http://<host>:8787` for first-run setup. Use an explicitly trusted reverse proxy for HTTPS.

## Upgrade from rc.3

Create and verify an encrypted backup, retain console access, and schedule a traffic interruption:

```bash
sudo exitlane-cli backup create /var/lib/exitlane/backups/pre-0.3.0-rc.4.elb
sudo exitlane-cli backup verify /var/lib/exitlane/backups/pre-0.3.0-rc.4.elb
```

Keep a protected off-appliance copy. Clone the rc.4 tag outside `/opt/exitlane` and run its Debian
installer. Validate version, login/MFA, saved settings, provider state, ingress identity,
management access and protected traffic afterwards. Follow [Upgrade and recovery](../upgrade-and-recovery.md)
for transaction, idempotence, retained schema/backup compatibility and bounded rollback limits.

## Provider status and known limitations

- Native NordVPN and Mullvad retain their existing supported integrations and historical live
  provider evidence; rc.4 qualification reruns the current deterministic/security regressions.
- PIA and Proton are **implemented and synthetically / native-kernel qualified; live
  commercial-provider connectivity remains unproven**. No account/profile proof is invented.
- Direct WireGuard IPv6 egress remains unavailable; protected IPv6 is blocked.
- Trusted management access and local console recovery remain deployment requirements.
- External independent penetration testing remains outstanding.
- Docker is experimental/unsupported, with no official published image. The retained pre-rc.4
  baseline has **44 HIGH package records across eight CVEs, 0 CRITICAL, 0 secrets and 0 Python
  advisories**. All then-fixable Trixie HIGHs were removed; the remaining eight lacked supported
  Debian 13 fixes. Candidate counts and Debian status must be freshly measured in the release
  receipt. Findings are neither suppressed nor waived; the HIGH/CRITICAL publication gate stays
  strict and no image publication is part of rc.4.

## Qualification and artifact checksums

The [qualification contract](../qualification/0.3.0-rc.4.md) separates historical evidence from
fresh final-main results and the actual post-publication public Proxmox gate. During preparation,
those gates remain pending until receipts exist.
The [2026-10-03 bounded receipt](../qualification/remaining-release-evidence-2026-10-03.md)
records completed native lifecycle supplements, OS disposition and candidate-helper evidence.
Live commercial interoperability and the actual published rc.4 public path remain uncompleted;
this preparation work does not publish a release.

The published GitHub release body records the exact final source SHA, CI/security runs, test
counts, native/public-PVE receipts, candidate image digest/scan and provider evidence limits.
The tag must resolve to that exact qualified source. Wheel/sdist SHA-256 values are recorded in
the release body and downloadable `SHA256SUMS`; verify downloaded artifacts against that file.
These source-dependent values are recorded outside the source commit to avoid self-referential
commit or artifact hashes. Release success requires the actual published public launcher to
create and install a fresh authorized disposable rc.4 appliance; failure must remain visible.
