# ExitLane 0.3.0-rc.1

ExitLane 0.3.0-rc.1 introduces direct Mullvad WireGuard egress alongside NordVPN and strengthens
provider switching, traffic protection and appliance recovery. This is a release candidate for
evaluation on the supported appliance baseline.

The release tag and application version are `v0.3.0-rc.1` and `0.3.0-rc.1`; the Python package version
is `0.3.0rc1`. The historical `v0.2.0` tag shipped runtime version `0.2.0-rc.1` and Python package
version `0.2.0rc1`. That historical mismatch does not change the upgrade path.

## Direct Mullvad WireGuard egress

- Sign in with a Mullvad account number through the authenticated WebUI. ExitLane registers one
  device and encrypts its account and WireGuard key state with the appliance master key.
- Select Mullvad as the active provider and connect to a country or relay. The router keeps its
  independent WireGuard ingress profile when the outbound provider or relay changes.
- Connection readiness requires the configured peer and a usable data path. Failed relay changes
  restore the previous proven generation where possible; otherwise protected forwarding stays blocked.
- Ending the session deletes only ExitLane's registered device. Uncertain remote results retain
  local identity for reconciliation instead of silently creating or deleting another device.

Follow the [Mullvad operator guide](../mullvad.md) for setup, DNS checks, protection settings,
sign-out and recovery. An active Mullvad app daemon or conflicting firewall table must be retired
before using the direct integration.

## Traffic protection and recovery

Mullvad routing protects forwarded clients, interface-bound probes and locally generated traffic
using the exact provider-assigned IPv4 source. Kernel local routing and normal management traffic
remain available. Exact source protection remains until reboot after disconnect or sign-out.

An active or pending generation restores mandatory routing protection before ingress starts after
boot or backup restore. This protection also applies when the backup has the optional killswitch
disabled. Explicitly reconnect after restore to establish a proven tunnel.

Management-route changes are serialized across application and CLI processes. WireGuard startup
waits for management-route preparation, preventing competing boot routines from deleting or
verifying each other's rules while the ingress is being created.

The optional ExitLane killswitch still controls client behavior after a deliberate disconnect:
enabled keeps clients blocked; disabled allows direct egress. A configured ingress cannot be
renamed through the provisioning API, and `wg-mullvad` is reserved for provider egress.

Restore quiesces the previous ingress, restores the database/master key/WireGuard files together,
revokes sessions and pending MFA state, reapplies routing protection and starts the restored ingress.
Failed restores recover the previous state while retaining protection when recovery cannot be verified.
Installer rollback preserves original executable and systemd-unit permissions inside private recovery
directories. Appliance package upgrades now enforce AnyIO `>=4.14.2,<5`, including existing installations.

## Authentication corrections

MFA challenge failures now commit their attempt accounting and expired-challenge cleanup before
returning an error. The attempt budget survives restarting sign-in, cancellation, client-IP changes
and service restarts until the original five-minute window expires or MFA succeeds. Challenge validation and one-time factor consumption are serialized so
concurrent requests cannot spend multiple recovery codes for one login.

Ending a NordVPN session uses normal provider logout, which invalidates its access token.
Generate a new token before signing in again; see [Authentication](../authentication.md).

## Supported platform and upgrade

The supported OS and architecture are **Debian 13 on `amd64`**. The qualified Proxmox configuration
is a **privileged LXC** with systemd, `/dev/net/tun` and permission to administer WireGuard, routing
and nftables. Docker, unprivileged LXC, other Debian releases and other architectures are not
supported release targets.

For a new installation, follow [Deployment](../deployment.md) and [Proxmox LXC](../proxmox-lxc.md).
For an existing `v0.2.0` appliance:

1. Create and verify an encrypted backup and keep a protected copy outside the appliance.
2. Keep console access available and schedule a client-traffic interruption.
3. Once published, run the installer from the trusted `v0.3.0-rc.1` checkout, outside `/opt/exitlane`.
4. Verify the new version, existing login/MFA, settings, ingress profile, provider connection,
   client DNS/public exit and management access before removing recovery material.

Older Nord-bound ingress forwarding rules migrate to provider-neutral routing while preserving
keys and peer configuration. Full procedures are in [Upgrade and recovery](../upgrade-and-recovery.md)
and [Backup and restore](../backup-and-restore.md).

## Known limits

- Mullvad egress is IPv4-only; protected IPv6 is blocked.
- One commercial provider is active at a time. Automatic relay/country failover, multihop and
  the complete Mullvad app feature set are outside this release.
- The trusted management network remains a deployment requirement. Direct public exposure of the
  management interface is unsupported; HTTPS uses the documented trusted reverse-proxy setup.
- Gateway operation requires root-level network administration on a dedicated appliance.
- Restored Mullvad identities must not run concurrently on cloned appliances. Signing out on the
  original revokes the device held in its backups. A revoked identity needs deliberate recovery.
- Appliance backups exclude host networking, operator defaults, custom units and NordVPN's
  host-wide state; operators must preserve or reconfigure those separately.
