# rc.4 qualification contract

This document defines the release evidence; it is not a receipt asserting that pending gates passed.
The [canonical v1 readiness matrix](../release-checklist.md#canonical-v1-readiness-matrix) tracks
how completion of this release boundary precedes the v1 candidate and separates optional Docker
support/publication from native release readiness.
The final merged-main SHA, checksums and measured results belong in the release body and retained
qualification report, rather than recursively changing the source they describe.

## Identity and evidence

- Runtime `0.3.0-rc.4`, package `0.3.0rc4`, annotated tag `v0.3.0-rc.4`.
- One reviewed release-preparation PR, immutable final-head approval and required checks.
- Fresh authoritative clean main, exact final source/tree identity and applicable hosted runs.
- Complete backend/frontend, lint/format, dependency/security, shell, i18n and package checks.
- Native namespace provider-egress/management/killswitch, DNS UDP/TCP, IPv4/IPv6 protection,
  switching/failure/rollback/readiness and no-plaintext assertions.
- Fresh clean supported native install; real rc.3 → rc.4 upgrade with verified encrypted backup,
  DB/key/auth/MFA/settings/provider/ingress preservation, idempotence, bounded injected installer
  failure/rollback and backup/restore/disaster recovery.
- Health/UI/authentication, bounded read-only security checks, service hardening and private modes.
- Wheel/sdist inspection, source attribution, metadata and SHA256SUMS; published downloads reverified.

Use [the complete checklist](../release-checklist.md) and [security checklist](../security/release-checklist.md).
PR-only dependency-review results are recorded against the approved PR head; final-main dependency
review is trigger-inapplicable, with fresh final-main pip-audit recorded separately.

The [disposable native lifecycle procedure](native-lifecycle.md) provides plan-first,
host/source-bound tooling and synthetic regression coverage for installation, retained
state, injected rollback and encrypted recovery. Its fixture tests are preparation,
not executed appliance qualification or authority to mutate an existing guest.

## Public Proxmox sequencing

The Product Owner explicitly authorizes two stages because the public bootstrap cannot resolve an
unpublished release. Complete all normal final-main gates and exact-source candidate helper/native
qualification before tagging/publishing. Immediately afterwards, execute the ordinary moving-main
public one-liner on the designated disposable PVE host and prove actual rc.4 resolution, helper
integrity, fresh creation and same-tag install. Record network/VLAN/private-DNS/default route/`_apt`
readiness/TUN, console/SSH policy/log/secret handling, service/health/first-run/auth and stop/start.

CT100 must not be modified and CT123 must not be used as fresh-create proof. Preserve guests unless
cleanup is separately authorized. Only actual stage-two evidence closes #87 or completes rc.4.
If the public path fails, retain evidence and prepare a reviewed follow-up; never move the tag.

## Docker candidate and strict publication boundary

**Docker remains experimental/unsupported. No official Docker image is published.**

D1–D7 source and historical [whole-host D6 qualification](docker-host.md) are included, without
converting synthetic/provider evidence into live interoperability or support claims. Rebuild the
exact rc.4 source for linux/amd64 with fresh package resolution and verify OCI version/source,
content, runtime dependencies, service/health, state/lifecycle, full Trivy report and SPDX SBOM.
Do not push, dispatch publication, create aliases or expose a package.

Requery Debian's authoritative tracker for every remaining CVE at candidate qualification. Retain

shared application dependencies and the supported native package separately: any applicable
blocking native/shared HIGH or CRITICAL still blocks the application release. Native operator-owned
OS updates remain a deployment responsibility and must be inspected on the qualification appliance.

The protected `ghcr-production` Environment, required Product Owner reviewer and exact release
identity remain necessary for a future, separately authorized first image publication. rc.4 source
publication grants none of that authority. #90 and #97 remain open at this boundary.

## Provider and assurance boundaries

PIA/Proton implementation and deterministic/native-kernel evidence are inherited from rc.3;
live commercial-provider connectivity remains unproven without authorized account/profile proof.
Native NordVPN remains supported; stock 5.4.0 is incompatible with the qualified Docker runtime
contract ([research](../nordvpn-container-research.md)). No capability expansion was adopted.
Daybreak reports remain dated internal defensive evidence, not external penetration testing.
