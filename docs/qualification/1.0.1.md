# Native v1.0.1 upgrade qualification contract

This is the release-specific contract for the published `v1.0.0` tag
`7973d3a6508c08a2949b88dad3750f43544cff48` to a reviewed `1.0.1`
candidate. It is a gate definition, not an appliance receipt or a release PASS.
The [historical rc.4 lifecycle contract](native-lifecycle.md) remains historical.
Use only separately authorized disposable Debian 13 amd64 native guests and
the private, source-bound lifecycle runner described there. Its plan mode
does not authorize execution.

The upgrade guest must start with the exact published v1.0.0 source and
installed package. The runner pins the full baseline commit and both package
versions. The v1 database must have the known v1 tables and schema objects,
their exact DDL, constraints, indexes and SQLite autoindexes. In particular,
neither `wireguard_peers` nor `wireguard_ingress_profile` exists before the
upgrade. A fresh published v1 install legitimately has no
`installed-version` marker; an existing marker must contain exactly `1.0.0`
with root-private metadata, and its presence/bytes may not change between
snapshot and certification. Seed and verify configured synthetic legacy WireGuard ingress through
the genuine v1 application before taking the pre-upgrade snapshot.

The runner creates a private certificate before invoking the ordinary 1.0.1
installer. It reads the actual legacy server and client config bytes, verifies
their snapshot hashes and metadata, matches the complete settings row
fingerprints, and derives each public key from the corresponding private key.
Private keys remain only in root-private guest files; they are excluded from
public logs and receipts. The certificate binds the old peer and profile
fields to those pre-upgrade bytes and settings. It cannot be built from the
post-upgrade state.
Genuine v1 server configs may contain repeated nonempty `PostUp` and
`PostDown` interface directives. The certificate parser permits only those
repeated hook keys; the complete server file bytes and metadata must still
match the pre-upgrade snapshot. Duplicate peer or identity fields are rejected.

After the successful installer, the runner first requires two HTTP health
successes within one stable systemd invocation. This read-only health route
does not adopt legacy peers. It then captures the first post-upgrade snapshot
before any peer or config API probe that could repair legacy state lazily.
The only permitted schema delta is the
two peer/profile tables, the one default-peer unique partial index, and four
expected SQLite autoindexes. All old schema objects and table columns must
remain byte-for-byte equivalent in the private snapshot. Unknown tables,
views, triggers, indexes, columns or changed DDL fail qualification.

Exactly one active default peer and one singleton ingress profile must be
present. The peer name and config name equal the old client name; description
is empty, its public key equals the old server peer and the public key derived
from the old client private key, and its tunnel IP equals the old client
address without `/32`. Status is active, `is_default` is 1, and revocation is
null. Its ID is a lowercase UUIDv4 hex value. Created and updated timestamps
must be identical UTC values inside the observed installer interval. The
profile endpoint, DNS, AllowedIPs and explicit keepalives must equal the old
client/server config, using 25 only when the respective setting was absent.
Its server public key equals the old client remote key and the public key
derived from the old server private key.

The existing preservation comparison still protects every old table row,
settings, master key, host defaults, WireGuard file bytes and metadata. Its
only exceptions are session access bookkeeping and append-only Activity
events. The special schema comparison is used solely for this first
successful pinned v1.0.0 to 1.0.1 upgrade. Rollback, restore, idempotence,
repeated installation and subsequent snapshot comparisons retain their strict
schema and row matching, including stable peer ID and timestamps.

Keep configuration, fixture, certificate, snapshots, logs and receipts under
the runner's root-private `0700` directory with `0600` files. Publish only
reviewed source identities, stage outcomes and explicit limits. The synthetic
inactive provider and empty cache/challenge/enrollment fixtures do not prove
active-provider restoration, populated-cache preservation, live commercial
interoperability or protected packets during upgrade. Those claims require
their own actual appliance evidence before a release PASS.
